# Правила составления Use Case

Собранные и согласованные правила описания систем сценариями использования (Use Case).
Объём — для описания системы: от Actor–Goal List до детализации ключевых сценариев.
База: Alistair Cockburn «Writing Effective Use Cases», Ivar Jacobson Use Case 2.0/3.0, RU-практика (Хабр, 2025), утверждённый шаблон проекта.

---

## 1. Ключевые понятия

- **Use Case (сценарий использования)** — описание того, как пользователь взаимодействует с системой для достижения конкретной цели. Система рассматривается как чёрный ящик: описывается «что», никогда — «как».
- **Название UC** — английское, по схеме «глагол + существительное», 3–5 слов, отражает бизнес-цель, а не техническую реализацию. Примеры: `Buy Goods`, `Register User`, `Generate Report`, `Log In to System`.
- **Актор** — роль (человек, организация или внешняя система), которая взаимодействует с системой ради цели. Основной (первичный) актор — владелец цели; вторичные — обслуживают сценарий (банк, почтовый сервис, провайдер авторизации). Временнóе событие (таймер) может быть актором.
- **Цель должна быть достигнута**: UC без доставки конечного результата («система обрабатывает») — это функция, а не цель.
- **include (включение)** — поведение включаемого UC выполняется всегда, как обязательная часть.
- **extend (расширение)** — поведение добавляется только при наступлении условия (опционально).
- Вложенность include/extend — не более 2 уровней.

### Поля документа заполняются на русском, кроме названия UC (английское — по правилу 1).

## 2. Поле «USE CASE / Название»

- Формат строки: `USE CASE 5 | Buy Goods`.
- **Номер** — уникальный в пределах проекта, не повторяется.
- **Название** — английский, «глагол + существительное», 3–5 слов, бизнес-цель, не реализация.
- Без аббревиатур без расшифровки.

## 3. Поле «Description» (Описание)

- **Назначение:** краткое описание бизнес-цели сценария.
- **Формат:** свободный текст, 1–2 предложения.
- **Требования:**
  - описать, кто инициирует сценарий и какой результат ожидает получить;
  - сфокусироваться на бизнес-ценности, а не на технических деталях;
  - настоящее время, активный залог;
  - не дублировать информацию из других полей (Trigger, Preconditions).
- **Пример:** `Покупатель напрямую обращается в нашу компанию, ожидает отправки товара и выставления счёта.`
- **Критерий качества:** после прочтения описания любой участник проекта должен понять, зачем существует этот Use Case.

## 4. Поле «Used by» (Используется в)

- **Назначение:** указание на родительский Use Case более высокого уровня, в контексте которого выполняется данный сценарий.
- **Формат:** `<Название родительского UC> (use case <номер>)`.
- **Требования:**
  - указывать только если данный Use Case является частью более крупного процесса;
  - ссылаться на существующий и описанный родительский Use Case;
  - если сценарий автономный — оставить поле пустым или указать «N/A».
- Ссылки вниз (на дочерние UC) — в тексте шагов: `(use case NN)`.

## 5. Поле «Preconditions» (Предусловия)

- **Назначение:** перечень условий, которые должны быть истинны до начала выполнения Use Case.
- **Формат:** список утверждений в настоящем времени.
- **Требования:**
  - каждое условие должно быть проверяемым и измеримым;
  - описывать состояние системы или данных, а не действия пользователей;
  - не включать тривиальные условия (например, «пользователь включил компьютер»);
  - все условия должны выполняться одновременно перед запуском сценария.

## 6. Поле «Success End Condition» (Условие успешного завершения)

- **Назначение:** описание состояния системы и бизнес-результата после успешного выполнения сценария.
- **Формат:** одно или несколько утверждений в настоящем времени.
- **Требования:**
  - описать конечное состояние системы (что изменилось, что создано);
  - указать бизнес-результат для актора и для системы;
  - результат должен быть измеримым и проверяемым;
  - не описывать процесс достижения результата.

## 7. Поле «Failed End Condition» (Условие неудачного завершения)

- **Назначение:** описание состояния системы при отмене, сбое или невозможности выполнения сценария.
- **Формат:** список утверждений, описывающих отсутствие изменений или откат.
- **Требования:**
  - указать, что НЕ произошло в системе;
  - описать, что система осталась в согласованном состоянии;
  - учесть возможные частичные изменения и их откат;
  - не описывать причины сбоя — только результат.
- Это «минимальная гарантия» (Cockburn): из поля выводятся негативные тест-кейсы.

## 8. Поле «Actors» (Акторы)

- **Назначение:** перечень всех участников сценария — людей, систем и организаций.
- **Формат:** список с кратким описанием роли каждого актора.
- **Требования:**
  - первичный актор (инициатор сценария) указывается первым;
  - вторичные акторы (вспомогательные системы, внешние сервисы) перечисляются следом;
  - для каждого актора указать его роль в контексте данного Use Case;
  - различать человеческих акторов и системных.
- Внутренние компоненты системы (хранилище, модули) акторами не считаются — граница UC «система как чёрный ящик».

## 9. Поле «Trigger» (Триггер)

- **Назначение:** описание события, которое запускает выполнение Use Case.
- **Формат:** краткое описание события в настоящем времени.
- **Требования:**
  - событие должно быть наблюдаемым и измеримым;
  - может быть внешним (действие актора, сообщение от системы) или временным (наступление даты);
  - не путать с предусловиями — триггер это событие, а не состояние;
  - один Use Case — один основной триггер.

## 10. Секция «DESCRIPTION» (Основной поток)

### Поле «Step» (Шаг)
- Нумерация шагов строго последовательная: 1, 2, 3, …
- Каждый шаг — атомарное действие, которое нельзя разделить на более мелкие без потери смысла.
- Нумерация начинается с 1 для каждого Use Case.
- Не пропускать номера шагов.
- Рекомендуется 3–9 шагов.

### Поле «Action» (Действие)
- Описывать действие от третьего лица в настоящем времени.
- Чётко указывать исполнителя: актор или система.
- Избегать технических деталей реализации.
- Одно действие = один шаг.
- Действие должно быть наблюдаемым и проверяемым.
- Не включать условные переходы в основной поток — для этого есть секция EXTENSIONS.
- При свободном порядке шагов — комментарий: «шаги 2–4 в любом порядке».

### Уровень технических деталей в шагах
- **Допустимы** механизмы, имеющие смысл для требований (безопасность, аудит, целостность данных) — например, «система сохраняет параметры защиты входа (state, nonce, код подтверждения PKCE)».
- **Недопустимы** детали реализации: файлы, методы, HTTP-статусы, маршруты (`GET /auth/login`, `302 Location: …`), конкретные форматы строк.
- **Критерий:** читатель без доступа к коду должен понять, ЗАЧЕМ это действие, а не только КАК оно сделано.

## 11. Секция «EXTENSIONS» (Расширения и исключения)

### Поле «Step» (Шаг ветвления)
- Формат ссылки: `<номер шага основного потока><буква>` (3a, 4a, 7a).
- Буква указывает на конкретное расширение шага.
- При нескольких расширениях одного шага — последовательные буквы: 3a, 3b, 3c.
- Расширение должно ссылаться только на существующий шаг основного потока.

### Поле «Branching Action» (Ветвящееся действие)
- Начинать с описания условия возникновения расширения.
- Описать альтернативный сценарий или обработку ошибки.
- Подшаги нумеруются в формате `<шаг><буква><цифра>`: 3a1, 3a2.
- При ссылке на другой Use Case указывать его номер в скобках: `(use case 44)`.
- После обработки расширения явно указать возврат в основной поток («Продолжить с шага N») или завершение сценария (успешное / с ошибкой).
- Расширение, заканчивающееся «в никуда» — ошибка.

### Порядок работы с расширениями
- Сначала исчерпывающе перечислить ВСЕ условия расширений (что система может обнаружить и обязана обработать), и только потом писать их обработку.
- Обязательно обойти по вторичным акторам: таймауты, отказы, дубли, недоступность — самые пропущенные условия.

## 12. Секция «VARIATIONS» (Вариации)

- **Поле «Step»:** номер шага основного потока, для которого существует вариация.
- Вариации не меняют бизнес-логику, а показывают альтернативные способы выполнения одного и того же шага.
- **Поле «Branching Action»:** перечислить все допустимые альтернативы выполнения указанного шага.
- Формат — маркированный список.
- Все варианты должны приводить к одному и тому же результату.
- Обычно применяется к шагам ввода данных, выбора способа оплаты, канала связи.

### Расширения против вариаций
- **Расширения** — ветвления потока: условие + шаги обработки; меняют ход сценария (отказ банка, отсутствие товара).
- **Вариации** — перечень допустимых технологических/данных вариантов без процедуры: каналы (телефон, факс, веб, EDI), способы оплаты (наличные, чек, карта), форматы данных. Поток не меняют.

## 13. Диаграмма Use Case

Графическое отображение Use Case выполняется с помощью диаграммы Use Case — стандартного способа визуализации функциональных требований. Два основных элемента: участник (actor) и прецедент (вариант).

### Основные элементы
- **Акторы (Actors):** роли внешних сущностей (люди, другие системы, таймеры), которые взаимодействуют с системой. Обозначаются «человечками». Название пишется в единственном числе.
- **Варианты использования (Use Cases):** отдельные функции или сервисы, которые система предоставляет актеру. Обозначаются овалом с глаголом в описании.
- **Границы системы (System Boundary):** прямоугольник, отделяющий внутренние функции системы от внешних актеров.

### Типы связей (отношений)
- **Ассоциация (Association):** сплошная линия. Показывает, какой актер связан с каким вариантом использования.
- **Включение (Include):** пунктирная стрелка с надписью `<<include>>`. Означает, что один вариант использования обязательно включает в себя выполнение другого (пример: «Оплатить заказ» включает «Проверить баланс карты»). Стрелка — к включаемому.
- **Расширение (Extend):** пунктирная стрелка с надписью `<<extend>>`. Означает необязательное или условное поведение (пример: к «Оплатить заказ» добавляется «Применить промокод»). Стрелка — к базовому.
- **Обобщение (Generalization):** сплошная линия с не закрашенным треугольником на конце. Означает наследование ролей или вариантов использования (пример: актер «Администратор» обобщает «Пользователь»). Треугольник — к более общему.

### Зачем нужна диаграмма
- **Согласование требований:** помогает заказчикам и разработчикам понять, что именно должна делать система.
- **Определение границ:** четко фиксирует, какие функции находятся внутри продукта, а какие за его пределами.
- **Основа для тестов:** позволяет тестировщикам заранее наметить основные сценарии проверки.

### Проверка диаграммы
- Каждый актор связан хотя бы с одним прецедентом (актор без связей = неучтенная потребность).
- Граница соответствует области системы.
- Направления стрелок include/extend верны.
- Не более ~12–15 прецедентов на диаграмме, иначе — разбить на поддиаграммы (по актору/подсистеме) или использовать упаковки.

## 14. Процесс описания системы (12 шагов)

1. **Назвать область и границы системы** (что внутри, что снаружи; список входов/выходов на границе).
2. **Перечислить акторов** — все человеческие роли и внешние системы за всё время жизни системы, а не только релиз 1.
3. **Перечислить цели** для каждого актора исчерпывающе.
4. **Собрать Actor–Goal List** — это функциональные требования 1-го уровня; приоритизировать, разложить по релизам.
5. **Зафиксировать summary-UC** (по одному на пару актор–цель) + построить диаграмму Use Case; проверка «актор без связи» — проверка полноты.
6. **Перераспределить:** объединить дубли, расщепить слишком широкие цели, добавить/убрать.
7. **Выбрать UC для детализации:** ключевые бизнес-цели, потоки с несколькими акторами/внешними системами, рискованные/сложные. Остальные — краткая форма.
8. **По каждому детальному UC:** предусловия, условие успешного завершения, условие неудачного завершения, стимул.
9. **Написать основной поток** (3–9 шагов, см. раздел 10).
10. **Исчерпывающе перечислить условия расширений** (до написания обработки).
11. **Написать обработку расширений** — каждое заканчивается возвратом в основной поток, отдельным успешным выходом или завершением с ошибкой.
12. **Вынести сложные подпотоки в дочерние UC** (include); объединить тривиальные; пересмотреть набор.

### Уровни детализации (работать breadth-first, от низкого к высокому)
| Уровень | Что записано |
|---|---|
| 1 | Имя основного актора и цель для каждого UC |
| 2 | Краткое описание / основной сценарий |
| 3 | Условия расширений (список исчерпан) |
| 4 | Шаги обработки расширений |

Уровень 4 — только после исчерпывающего списка уровня 3 (перемешивание — «ловушка энергии»: обработку пишут, пока список неудач не закончен).

## 15. Общие требования к документу Use Case

### Стиль написания
- Использовать простой, понятный язык без жаргона.
- Придерживаться единой терминологии во всех полях документа (одна сущность — одно имя).
- Предпочитать активный залог пассивному.
- Писать в настоящем времени.
- Избегать неоднозначных формулировок («может быть», «иногда», «при необходимости»).

### Форматирование
- Использовать табличную структуру для наглядности.
- Выделять заголовки секций жирным шрифтом.
- Применять отступы для подпунктов и подшагов.
- Нумерованные списки — для последовательных действий, маркированные — для вариантов.

### Логическая целостность
- Все расширения должны ссылаться на существующие шаги основного потока.
- Все ссылки на другие Use Case должны указывать на реально существующие сценарии.
- Предусловия не должны противоречить условиям завершения других Use Case.
- Основной поток должен приводить к Success End Condition.
- Все критические исключения должны быть описаны в EXTENSIONS.

## 16. Чек-лист проверки качества Use Case

Перед утверждением документа убедитесь, что выполнены все пункты:

- [ ] Поле USE CASE содержит уникальный номер и корректное название (EN, глагол+сущ., 3–5 слов).
- [ ] Description кратко и понятно описывает бизнес-цель.
- [ ] Used by ссылается на существующий родительский Use Case (или указано N/A).
- [ ] Все Preconditions проверяемы и описывают состояние системы.
- [ ] Success End Condition измерим и отражает бизнес-результат.
- [ ] Failed End Condition описывает согласованное состояние системы.
- [ ] Все акторы идентифицированы, первичный актор указан первым.
- [ ] Trigger описывает конкретное наблюдаемое событие.
- [ ] Шаги основного потока пронумерованы последовательно без пропусков.
- [ ] Каждое действие атомарно и имеет явно указанного исполнителя.
- [ ] Основной поток приводит к Success End Condition.
- [ ] Все расширения ссылаются на существующие шаги.
- [ ] Для каждого расширения указано условие возникновения.
- [ ] Указан возврат в основной поток или завершение сценария после расширения.
- [ ] Вариации перечисляют все допустимые альтернативы выполнения шага, приводящие к одному результату.
- [ ] Терминология единообразна во всём документе.
- [ ] Отсутствуют технические детали реализации (кроме допущенных механизмов: безопасность/аудит).

## 17. Критерии «хорошего» и «плохого» Use Case

1. **Четкость и однозначность** — название отражает суть, шаги без двусмысленности.
   Плохо: «Обработать заказ» — неясно, что значит «обработать».
2. **Полнота покрытия** — описаны основной поток, альтернативные сценарии и исключения, взаимодействие всех акторов.
   Плохо: «Оплата прошла успешно» — не описана обработка ошибок.
3. **Практическая полезность** — из сценария понятно, что реализовывать; есть предусловия и постусловия.
   Плохо: «Клиент взаимодействует с системой» — слишком абстрактно, неясно, зачем нужен бизнесу.
4. **Структура и читаемость** — стандартизированная структура, пронумерованные шаги.
   Плохо: «стена текста» без логического разделения.
5. **Масштабируемость и гибкость** — новое условие добавляется без переписывания; логика не смешивает несвязные функции; шаг не завязан на реализацию.
   Плохо: «Клиент вводит номер карты из 16 цифр» (завязка на реализацию); «Забронировать отель и заказать такси» (несвязные функции в одном UC).

Плохой Use Case создает иллюзию работы, но на практике приводит к пробелам в разработке и неожиданным багам.

---

## 18. Когда Use Case не подходят (ограничения метода)

- Преобладание внутренних правил взаимодействия объектов над действиями пользователя (доменные сущности с уникальными жизненными циклами и взаимосвязями) — использовать state machine / диаграммы классов.
- Нефункциональные требования (производительность, безопасность, масштабируемость) — Use Case не покрывают.
- Временнáя последовательность и параллельные события (например, уведомления после каждого действия) — не отражаются.
- Очень большие системы — Use Case громоздкие: держать краткую форму, детализировать выборочно; поддержка актуальности требует усилий.
- Качество зависит от опыта автора — обязательна самопроверка по чек-листу.

---

## 19. Объём для описания системы

- **Всегда:** полный Actor–Goal List + все UC в краткой форме (ID, название, основной актор, цель, стимул).
- **Детализация** (основной поток + расширения): ключевые бизнес-цели, многоакторные/внешние потоки, сложные и рискованные сценарии — обычно 30–60 % набора.
- **Остальные UC** — краткая форма; кандидаты на детализацию в следующих релизах.

---

## 20. Связь с тестовыми сценариями

- Каждый основной поток (MSS) = один базовый тестовый сценарий.
- Каждое расширение = один дополнительный тест-кейс (негативный/альтернативный путь).
- Маппинг в таблицу тест-сценариев (7 колонок): «Код сценария», «Наименование сценария», «Номер шага», «Описание шага», «Входящие данные», «Результат шага», «Примечание».
- В «Примечании» — трассируемость на Use Case: `UC-01/3a` → тест-кейс.
